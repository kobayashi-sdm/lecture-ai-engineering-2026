## 宿題

- 取り組んだレベル：基礎
- やったこと：ベクトル検索で返す件数 `RAG_TOP_K` を、`app/config.py` で 5 → 3 に変えた。差分は [results/hw_change_config.diff](results/hw_change_config.diff)。指示文・docstring は変えていない。
  - 狙い：入力トークンを減らしたときに、複数ページにまたがる根拠が落ちるかを確かめる。
- 比較した質問と、固定した条件：
  - 質問A：第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか。根拠は第3回 p.13、39、40 で、複数ページにまたがる。
  - 質問B：演習と同じ LoRA／QLoRA の質問。根拠は第2回 p.52 の1ページ。
  - モデル gemini-3.5-flash-lite、通常の起動のベクトル検索、対象は第1〜3回の本講義214ページ。質問Aは変更前後で2回ずつ、質問Bは1回ずつ実行した。

  - 変更後、エージェントは自分で2回目の検索をした。検索語は1回目が「長期メモリ 日々のメモ Claude Code」、2回目が「Claude Code 自動メモリ 毎回先頭200行」。どちらも p.40 を取得し、「毎晩の見直しで基準を超えたものだけ長期メモリへ移す」という答えは変更前と同じだった。

- 改善した例と、残る失敗・制約：
  - 改善：質問Bは入力が 3,037 → 2,077 トークンで約32%減、費用は約19%減で、回答と根拠は変わらなかった。時間は 2.17 → 5.18 秒と増えたが、1回ずつの計測で、ばらつきと区別できない。
  - 逆効果：質問Aは検索が1回増え、入力トークンは約1.9倍、費用は約1.3倍になった。件数を減らしても、足りない分をエージェントが取りに行くので、複数ページの質問では安くならない。
  - 残る失敗：メモリの基本を示す模式図の p.13 は、変更後は一度も取得されなかった。変更前も2回中1回しか引用していない。回答は p.39、40、65 で成り立っていて、p.13 がなくても誤りにはならなかった。
- 気づき・疑問：
  - 件数を減らしたぶんを、エージェントの再検索が補った。ただ、2回目の検索語は2回とも「Claude Code」を含み、日々のメモを狙った語ではなかった。p.40 が取れたのは、p.39 と p.40 が隣り合う実装例のページで、似た本文だったからだと思われる。
  - 件数を固定で決めるより、単一ページで足りる質問は少なく、またがる質問は多く取る、のように質問によって変えられないかと思った。

## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified を調べた。
  - データ：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
  - 作成元：OpenAI「Introducing SWE-bench Verified」（2024/8）
  - 後日の見直し：OpenAI「Why we no longer evaluate SWE-bench Verified」（2026/2）
- 読んだ問題（4件）：
  - astropy-12907（15分〜1時間）：組み合わせたモデルをさらに入れ子にすると、変数どうしが独立かどうかを表す行列が誤って計算される。
    - 再現例があるので、何がおかしいかは分かる。ただ、入れ子をどう処理すべきかはライブラリの内部を読まないと分からず、自分では解けない。
    - LLMにとって難しい点：該当の関数を探し当て、再帰的な処理のどこが誤りかを特定すること。
  - django-13568（15分〜1時間）：ユーザー名の一意性を `UniqueConstraint` で指定しても、システムチェックが「一意でない」と誤って警告する。
    - 書き手自身が「バグかどうか分からない」と書いている。
    - 直す方針は文中に書かれている。ただ、制約が条件付き（一部の行だけに効く）の場合を除外すべきかどうかは、問題文から読み取れない。
  - xarray-3151（15分〜1時間）：値がすべて同じ座標でも、昇順・降順に並んでいないとデータの結合がエラーになる。
    - 再現コードと「期待する出力」が書かれていて、問題としては明確。
    - 合格の判定は、追加された1件のテストと、壊れていないかを見る既存のテスト66件で行う。
  - astropy-13579（1〜4時間）：3次元の座標変換（WCS）を2次元に切り出すと、座標からピクセルへの変換結果だけがおかしくなる。
    - 修正は21行と少ないが、座標変換の分野知識が要る。
    - LLMにとって難しい点：短い修正にたどり着くまでの原因の特定。
- 作成の人数と手順：
  - 元データ：人気のPythonリポジトリ12個にある、解決済みのGitHubのissueと、それを直したPR。
    - 採点は、PRで追加されたテスト（直す前は失敗し、直した後は通る）と、既存のテスト（前後どちらでも通る）を実行して行う。両方通れば合格。
    - モデルにはissueの文章とコードだけを渡し、テストは見せない。
  - 検証：
    - 作業者は、Pythonの経験があるソフトウェア開発者93人。OpenAIの技術者が事前に正解を付けた50件で選考テストを行い、合格した人だけが参加した。
    - 1,699件を、1件につき3人が別々に判定した。判定の観点は「問題文があいまいでないか」「テストが正しい修正を落とさないか」の2つで、それぞれ0〜3の4段階。
    - 3人のうち1人でも2以上を付けた件は除いた。その結果、68.3%が除外された。
  - 選び方：残った中から、難しい件（1時間以上）をできるだけ残し、あとは無作為に選んで500件にした。
    - 内訳：15分未満が196件、15分〜1時間が259件、1時間以上が45件。
  - 後日の見直し（2026/2）：
    - o3 が64回試して安定して解けなかった138件を、1件につき6人以上で見直した。その結果、59.4%に不備があった（テストの合格条件が実装の細部を決めつけている、問題文にない機能まで試している、など）。
    - 主要なモデルが、正解の修正（gold patch）をそのまま再現できた。つまり問題が学習データに混入していた。
    - そのため OpenAI は、このベンチマークのスコアを報告するのをやめた。
- 結果：

  | | 今日の評価セット | SWE-bench Verified |
  |---|---|---|
  | 規模 | 10件 | 500件（1,699件から選んだ） |
  | 作成 | 講師1人が作問 | 実際のissueとPRから集めた |
  | 検証 | 講師1人 | 選考を通った開発者が1件3人 |
  | 採点 | 人とLLMが基準で判定、「回の表示」はコード | テストの実行だけ（コード） |
  | 判定の対象 | 回答の文章（基準で判定） | 修正したコード（テストで判定） |

- 気づき・疑問：
  - テストで採点すると判定は機械的に決まる。それでも、テストや問題文そのものの不備は防げず、93人が1件3人で検証した後でも残っていた。演習で「まだ決めていないこと」があると LLM が unsure を出したのと同じで、採点のぶれの原因は採点者よりも基準や正解の側にあることが多いと感じた。
  - 公開データで作るベンチマークは、いずれ学習データに混入する。自分の評価セットは公開せず、新しい失敗を足して育てていく方が測定として長持ちすると思った。
  - 疑問：除外の基準を「3人のうち1人でも」と厳しくしたことで、難しいけれど正当な問題まで除かれ、難易度が易しい側に偏っていないか。
